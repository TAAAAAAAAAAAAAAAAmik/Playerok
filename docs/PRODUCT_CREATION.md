# Создание товара на Playerok

## Что выяснено про API

Разбор рабочей неофициальной библиотеки
[alleexxeeyy/PlayerokAPI](https://github.com/alleexxeeyy/PlayerokAPI).

Ключевое:

* Эндпоинт один — `POST/GET https://playerok.com/graphql`.
* **Авторизация — по кукам, а не по заголовку `Authorization`**: `token` (JWT) плюс
  кука DDoS-Guard `__ddg5_`/`__ddg3`. Кука умирает при смене IP, User-Agent или
  TLS-отпечатка. Из-за этого «голые» запросы часто ловят проверку бота, а браузер
  проходит её сам — поэтому первый этап делаем на Selenium.
* Чтение справочников идёт **persisted-запросами**: `operationName`,
  `variables` и `extensions.persistedQuery.sha256Hash` вместо текста запроса.
  Хэши меняются при каждой сборке фронта, и устаревший сервер отвергает —
  например, `games` отвечает «Access denied». Поэтому их не зашивают:
  `query_sniffer` открывает сайт браузером, читает журнал сети и снимает
  актуальные пары operationName → hash в `.playerok_queries.json`.
  Обновление запускается само при отказе операции, вручную —
  `python query_sniffer.py`.
* Запись (`createItem`, `publishItem`) — обычные мутации с полным текстом запроса.
* `createItem` принимает картинки отдельным аргументом `$attachments: [Upload!]!`
  по multipart-спеке GraphQL (`operations` + `map` + пронумерованные файлы).
* Созданный товар попадает **в черновик**. На продажу его выставляет `publishItem`
  с `priorityStatuses: [id]`; бесплатному размещению соответствует статус с
  `price == 0` из `itemPriorityStatuses`.

## 9 шагов мастера

Мастер — **модальное окно**, а не отдельная страница: открывается кнопкой
«Выставить товар» в профиле или «Продать» в нижней навигации, адрес при этом не
меняется. Заголовки шагов видны в шапке окна и служат маркерами в коде
(`STEP_TITLES`).

| № | Заголовок в UI | Что делаем | Что в API |
|---|----------------|------------|-----------|
| 1 | Выберите раздел товаров | поиск «Поиск игр и приложений», клик по игре — сразу переводит дальше | `games` → `game.id` |
| 2 | Выберите категорию | клик по категории, «Далее» | `GamePageCategory` → `category.id` |
| 3 | Способ передачи | клик по варианту, «Далее» | `gameCategoryObtainingTypes` → `obtainingTypeId` |
| 4 | Характеристики | чипы категории, «Далее» | `input.attributes` |
| 5 | Фото 1/10 | загрузка файлов, «Далее» | `$attachments` |
| 6 | О товаре | «Название товара», «Описание товара», «Далее» | `input.name`, `input.description` |
| 7 | Цена | «Цена товара» (рядом «Доход»), «Далее» | `input.price` |
| 8 | Данные товара | «Комментарий» и др., кнопка **«Сохранить»** | `input.dataFields` (только `ITEM_DATA`) |
| 9 | Выберите сервис | Премиум / Обычный (бесплатно) / Выставить позже | `itemPriorityStatuses` → `publishItem` |

⚠️ На девятом шаге **по умолчанию отмечен платный «Премиум»** (19 ₽ на момент
разбора). Код сначала кликает нужный вариант, затем проверяет текст кнопки: если
в нём остались «₽» или «Премиум», а размещение выбрано бесплатное — публикация
прерывается с ошибкой, чтобы не списать деньги. Вариант `later`
(«Выставить позже») оставляет товар черновиком — им удобно проверять сценарий.

Поля с типом `OBTAINING_DATA` заполнять не нужно — их вводит покупатель при заказе.

## Этап 1 — Selenium (сейчас)

Код: `selenium_creator.py`, диалог бота: `product_flow.py`, команда `/create`.

Настройка в `.env`:

```
PLAYEROK_COOKIES=token=eyJ...
SELENIUM_HEADLESS=0
SELENIUM_PROFILE_DIR=.chrome-profile
CHROME_BINARY=
CHROMEDRIVER_PATH=
CHROMEDRIVER_ARGS=
SELENIUM_MOBILE=0
```

`SELENIUM_MOBILE=1` переводит браузер в мобильный режим (Pixel 7, 412×915,
мобильный User-Agent и тач) — у Playerok мобильная вёрстка отличается от
десктопной, и селекторы нужно подгонять под ту, что видит пользователь.

Токен берётся из DevTools браузера (Application → Cookies → playerok.com → `token`).
Куку DDoS-Guard копировать не нужно — она привязана к IP, браузер получит свою.
Альтернатива — один раз войти руками в профиле `SELENIUM_PROFILE_DIR`, дальше
сессия переиспользуется.

Запуск на сервере (venv, Chrome, Xvfb, systemd) — см. [DEPLOY.md](DEPLOY.md).

Запуск без Telegram, для проверки сценария:

```bash
bash run_check.sh <token>      # запишет токен в .env, прогонит мастер,
                               # соберёт скриншоты и лог в tar.gz
```

Адрес страницы мастера не зашит: шаг 1 читает build-манифест Next.js
(`window.__BUILD_MANIFEST.sortedPages`) и берёт оттуда маршруты, похожие на
создание товара. Полный список маршрутов сайта сохраняется в
`debug/<дата_время>/routes.txt`.

Каждый шаг сохраняет скриншот и HTML-дамп в `debug/<дата_время>/` — по ним
подгоняются селекторы, если вёрстка Playerok изменилась. Бот присылает эти же
скриншоты в чат по ходу выполнения.

Селекторы намеренно текстовые (ищем по подписи, placeholder, `aria-label`), потому
что классы у Playerok сгенерированы и меняются при каждой сборке фронта.

### Что проверено

* Все 9 шагов прогнаны на макете, повторяющем реальный мастер (мобильная
  вёрстка, headless Chromium): открытие модалки из профиля, поиск и выбор игры,
  категория, способ передачи, чипы характеристик, загрузка файла,
  название/описание, цена, комментарий и «Сохранить», выбор размещения.
* Проверены оба безопасных варианта девятого шага: `free` жмёт «Выставить
  бесплатно», `later` — «Сохранить» (черновик).
* Проверена защита от платной кнопки: если вариант размещения не переключился,
  шаг падает и ничего не нажимает.
* **Живой прогон пройден полностью**: 30.07.2026 на реальном аккаунте мастер
  отработал все 9 шагов (Telegram → Звезды → По @username → 100 звёзд → фото →
  название/описание → 145 ₽ → комментарий → размещение `later`).
* Из контейнера разработки playerok.com недоступен (политика сети отвечает 403
  на CONNECT), поэтому здесь сценарий гоняется по макетам, а живой прогон — на
  сервере через `run_check.sh`.

## Этап 2 — создание запросами (сейчас основной путь)

Код: `api_creator.py`, транспорт — `transport.py`. Режим выбирается в `.env`:

```
CREATE_MODE=api       # запросами (по умолчанию)
CREATE_MODE=browser   # прогон мастера в Selenium — запасной путь
```

Порядок вызовов повторяет шаги мастера:

| Шаг | Запрос | Что получаем |
|-----|--------|--------------|
| 1 | `games` | `gameId` по названию игры |
| 2 | `GamePage` → `GamePageCategory` | `gameCategoryId` и `options` категории |
| 3 | `gameCategoryObtainingTypes` | `obtainingTypeId` |
| 4 | `options` категории | `attributes` = `{field: value}` |
| 5 | `gameCategoryDataFields` | `dataFields` — только поля `ITEM_DATA` |
| 6 | файлы с диска | вложения `createItem` |
| 7 | `createItem` | черновик товара |
| 8 | `itemPriorityStatuses` | статус размещения (бесплатный — с `price == 0`) |
| 9 | `publishItem` | публикация |

При `placement="later"` шаги 8–9 пропускаются: товар остаётся черновиком.

### Диалог в боте: два источника пунктов

Справочники Playerok отдаёт только своему фронту: `SellGames` отвечает
«Access denied» даже с актуальным хэшем, свежими куками и запросом из
браузера. Поэтому кнопки диалога бот берёт из одного из двух источников —
и выбирает его сам на первом шаге `/create`:

* **каталог** (`source="catalog"`) — если `.playerok_catalog.json` уже знает
  игры. Тогда Chrome не открывается вовсе: игра, категория, способ передачи и
  характеристики читаются из каталога, а товар создаётся `createItem` и
  выставляется `publishItem`;
* **мастер в браузере** (`source="wizard"`) — если каталог пуст. Бот держит
  открытый мастер (`wizard_session.py`), читает с его экрана пункты, показывает
  их кнопками, а выбор пользователя превращает в клики — и попутно наполняет
  каталог, так что следующий `/create` уже пойдёт запросами.

Браузерный путь даёт:

* названия всегда совпадают с сайтом — они с него и взяты;
* подписи полей («Комментарий») берутся с текущего экрана, поэтому бот
  спрашивает ровно то, что нужно этой категории;
* создание идёт проверенным путём — тем самым, что прошёл 9/9 на живом
  аккаунте.

Порядок шагов повторяет мастер: игра → категория → способ передачи →
характеристики → **фото** → название → описание → цена → данные товара →
размещение. Пункты читаются из DOM (самый внешний элемент с коротким текстом
и без вложенных пунктов) — иначе чипы характеристик склеиваются в одну строку.

Сеанс один на процесс, живёт 15 минут без действий и закрывается при отмене,
ошибке или завершении.

### Каталог идентификаторов и создание запросами

Справочники по API закрыты, но их получает сам фронт — и пока бот идёт по
мастеру, `catalog.py` подслушивает ответы через журнал сети (CDP
`Network.getResponseBody`) и складывает в `.playerok_catalog.json`
идентификаторы игры, категории, способа передачи, характеристик и полей.

Отсюда правило: **первый товар создаётся браузером**, а дальше — и новые
товары, и копии — идут **запросами**: `createItem` + `publishItem`, без Chrome,
за секунды. Если каталог связку не знает или запрос не прошёл, шаг молча
уходит на браузерный путь, так что сценарий не ломается.

Это же снимает старую беду с публикацией: клик по «Выставить» в мастере
оставлял объявление в черновиках, а `publishItem` возвращает статус товара,
поэтому бот пишет «Опубликован, статус: …» только когда сервер это подтвердил.

### Скидка

В браузерном пути цена вводится как обычно, а на том же шаге бот ищет поле
скидки и ставит `PLAYEROK_DISCOUNT` (по умолчанию 27%). Если у категории такого
поля нет, шаг не падает — в ответе будет «скидку задать не вышло», цена
останется исходной.

В запросах отдельного поля скидки нет: в `CreateItemInput` его не существует,
и лишнее поле схема встречает обезличенным «Something went wrong». Скидку
площадка рисует сама, когда цена стала ниже прежней (`prevPrice`), — поэтому

1. `createItem` создаёт черновик по цене «до скидки»
   (`цена / (1 − скидка)`, для 149 ₽ и 27% это 204 ₽);
2. `updateItem` опускает цену до той, которую назвал продавец.

Покупатель видит зачёркнутые 204 ₽, −27% и 149 ₽ к оплате, а продавец получает
ровно свои 149 ₽. Если второй запрос не пройдёт, бот не публикует товар и прямо
говорит, что черновик остался по цене до скидки: молча продавать дороже, чем
просили, нельзя. Отключается скидка через `PLAYEROK_DISCOUNT=0`.

### Шаблоны и копии

Каждый успешно выставленный товар сохраняется в `.playerok_templates.json`:
игра, категория, способ передачи, характеристики, название, описание, цена,
скидка, пути к фотографиям и поля товара.

`/create` предлагает два пути:

* **🆕 Создать товар** — обычный проход по мастеру;
* **📋 Шаблонная копия** — выбрать сохранённый товар, и бот повторит его сам,
  без вопросов, **заменив комментарий покупателю** на новый: приветствие,
  суть и концовка собираются из вариантов, поэтому копии не выглядят дублями.
  Это важно, потому что бесплатных объявлений на площадке ограниченное число,
  а одинаковые описания она не любит.

### Публикация

На девятом шаге рядом стоят «Выставить бесплатно», «Выставить Премиум за 19 ₽»,
«Выставить позже» и «Сохранить». Слово «Выставить» есть даже у черновика,
поэтому кнопка подбирается строго под выбор: для бесплатного размещения —
с «Выставить», но без «позже» и без цены. После нажатия бот проверяет, что
мастер закрылся: если экран остался прежним, товар не выставлен, и об этом
сообщается вместо ложного успеха.

`api_creator.py` остаётся рабочим путём для случая, когда Playerok откроет
справочники по API: он проходит те же 9 шагов запросами.

**Слабое место запросного пути — `itemPriorityStatuses`.** Создание идёт
обычными мутациями с полным текстом и от сборки фронта не зависит, а статусы
приоритета запрашивались только persisted-операцией. Стоило хэшу устареть, и
публикация утягивала за собой браузер со сниффером — на сервере без Chrome это
тупик, при том что сам товар создавался нормально.

Поэтому при отказе тот же запрос повторяется **полным текстом**
(`PRIORITY_STATUSES_QUERY`): сервер обычные запросы исполняет — на неизвестное
поле он отвечает `GRAPHQL_VALIDATION_FAILED`, то есть текст доходит до
валидатора. Аргументы подставляются литералами, чтобы не объявлять типы
переменных и не угадывать их написание в схеме. Браузер остаётся последним
средством, а не первым.

**`mayBePublished`** — сервер сам сообщает, можно ли выставлять товар.
`createItem` и `publishItem` теперь запрашивают это поле вместе с
`statusDescription`, и если публиковать нельзя, бот говорит об этом сразу после
создания черновика, а не отказом без причины на девятом шаге.

### Транспорт

Прямые запросы Playerok отбивает: перед API стоит DDoS-Guard, который смотрит
на TLS-отпечаток и куку `__ddg*`, привязанную к IP и User-Agent. Поэтому:

* запросы идут через `curl_cffi` с `impersonate="chrome"`;
* куки и User-Agent берутся из браузерной сессии (`.playerok_cookies.json`),
  обновляются Selenium'ом при отказе, но не чаще раза в 5 минут;
* persisted-операции отправляются **POST**-ом с JSON-телом: GET без
  `content-type` Apollo блокирует как возможный CSRF;
* если ничего не помогло, запрос выполняется прямо в браузере через `fetch` на
  открытой странице — там куки, UA и TLS совпадают по определению
  (`PLAYEROK_BROWSER_TRANSPORT=1` включает этот путь сразу);
* `createItem` шлёт файлы multipart-телом, собранным вручную: `curl_cffi`
  не принимает `files=`.

Об ошибках сервер рассказывает скупо, поэтому из ответа выбирается всё, что в
нём есть: текст, `extensions.code`, поле ввода и `path`. Имя операции у
multipart-запроса достаётся из его части `operations` — иначе `createItem`
жаловался бы безымянным «?», по которому не понять, какой шаг упал.

### Что проверено

Полный цикл прогнан на локальном сервере, отвечающем как Playerok: все 9 шагов,
правильные `operationName` и переменные, multipart с файлом и картой вложений,
выбор бесплатного статуса, `publishItem` с `priorityStatuses`, режим черновика
и понятные ошибки при неверных названиях. На живом аккаунте путь через браузер
подтверждён полностью; запросный — после того, как транспорт научился проходить
защиту.
